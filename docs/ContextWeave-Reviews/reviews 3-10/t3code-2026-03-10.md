## Flaws Found

### P0 (Critical — blocks adoption)

1. **Confidence is lexical, not semantic — HIGH confidence on wrong answers.** "state management" query returned desktop update test state objects with HIGH confidence. "error handling patterns" returned `const error = versionProbe.failure;` with HIGH confidence and VERY_LOW uncertainty. The confidence score reflects retrieval coverage (how many pivots were hit) not answer quality (whether the results answer the question). This makes confidence untrustworthy — I cannot skip verification when confidence is HIGH, which eliminates the primary value proposition.
   - **Root cause:** Confidence is computed from pivot/dependency coverage ratios in the retrieval pipeline, not from semantic similarity between query intent and returned symbols.
   - **Fix:** Add a semantic reranking pass after retrieval. Score each returned symbol against the query embedding. Confidence should reflect "do these results actually answer the question" not "did we find symbols with matching terms."

2. **Flow tracing cannot cross WebSocket/HTTP/event boundaries.** `cw_flow` is limited to static AST call edges. In an app where the primary architecture involves WebSocket communication between client and server, this makes flow tracing nearly useless for the most important flows. All 10 paths from `dispatchCommand` went into `LRUCache` internals instead of tracing to the server handler.
   - **Root cause:** AST-only edge resolution. No protocol-aware or convention-aware bridging (e.g., matching WS method names on client to route handlers on server).
   - **Fix:** Add configurable "bridge edges" for common patterns: WebSocket method dispatch (client `request("methodName")` → server `case "methodName"`), HTTP routes, event emitters/listeners. Detect these automatically from code patterns.

3. **Broad/architectural queries fail — 14% budget utilization on architecture query.** Asked for "complete architecture of the orchestration system" with 8,000 token budget. Got 1,114 tokens (14%) — mostly type skeletons and `yield* OrchestrationEngineService` one-liners. The `OrchestrationEngineShape` interface (the most important file) was reduced to a 4-line class declaration without the interface body. For the most valuable use case (understanding architecture), CW performs worst.
   - **Root cause:** Identified by CW diagnostics as `packing_scatter` — 10 files at 2.0 symbols/file. The packer spreads budget too thin across many files instead of deeply covering the most important ones.
   - **Fix:** For broad queries, use "story-complete" packing (as suggested in CW's own diagnostics). Prioritize depth over breadth — better to show 3 files completely than 10 files as skeletons.

### P1 (Important — degrades quality)

1. **Noise symbols pollute results — `onNone`, `onSome`, `gitShowFileAtRef` in OrchestrationEngineService query.** When querying for a specific symbol, the budget is consumed by unrelated symbols that happen to be in nearby files or share common AST patterns. The `OrchestrationEngineService` capsule included `onNone: () => undefined` from `CheckpointReactor.ts` — a 1-line arrow with zero semantic connection.
   - **Root cause:** Once a file is selected for inclusion, the packer includes additional symbols from that file to fill budget, without checking relevance to the query.
   - **Fix:** Score ALL packed symbols against the query, not just pivot symbols. Drop filler symbols that score below a relevance threshold.

2. **Capsule follow-up suggestions are consistently low-quality.** Across all tasks, suggested follow-ups were either irrelevant (`fileSystem` for orchestration query, `OrchestrationProject` type for architecture query) or trivially small (1-line symbols like `isWebSocketResponseEnvelope`). The scoring mechanism (e.g., score 267.98 for `Server` class, 228.35 for `error` variable) doesn't correlate with usefulness.
   - **Root cause:** Follow-up scoring appears to use centrality or reference count, not query relevance. A frequently-referenced symbol like `Server` scores high regardless of whether it helps answer the current question.
   - **Fix:** Score follow-ups by marginal information gain relative to what was already shown, weighted by query relevance.

3. **Test files consume significant budget in capsules.** Task B capsule included 7 test response snippets from `wsServer.test.ts` (token cost ~400). The `ProviderCommandReactor` query included test helpers `asProjectId` and `asTurnId`. Test code rarely helps understand architecture; it should be deprioritized unless the query is explicitly about testing.
   - **Root cause:** Test files have high edge counts (they import and call many symbols) so they score well in retrieval.
   - **Fix:** Apply a test-file penalty in `review` and `feature` modes. Only boost test files in `debug` mode.

4. **Stats tool claims 91% savings — measured savings were -4%.** `cw_stats` estimates Grep+Read cost at ~169,947 tokens by assuming you'd read every file end-to-end. My actual measured Grep+Read cost across 3 tasks was 6,370 tokens vs CW's 6,625 tokens. The comparison methodology is fundamentally misleading.
   - **Root cause:** The baseline estimation assumes the naive worst case (reading full files) rather than how a skilled user actually uses Grep (targeted pattern → targeted read of relevant lines only).
   - **Fix:** Use a more realistic baseline: estimate ~200 tokens per Grep hit + ~300 tokens per targeted Read section. Or better: track actual session comparisons and report measured savings.

### P2 (Moderate — papercut)

1. **`[previously shown]` summaries waste tokens.** In subsequent capsules, previously-returned symbols appear as `[previously shown]` with abbreviated content. This is good dedup behavior, but the summaries still consume tokens without adding new information. The "error handling patterns" capsule's top result was `[previously shown] const error = versionProbe.failure;` — a previously-shown irrelevant result taking up space.
   - **Fix:** Fully exclude `[previously shown]` symbols from capsules unless they're the primary answer. Save the budget for new symbols.

2. **Duplicate follow-up suggestions.** The WebSocket protocol capsule suggested `cw_read(file: "ProviderHealth.ts", symbol: "error")` twice with the same score (228.35). Dedup follow-up suggestions.

3. **`cw_overview` query focus section is too shallow.** Lists matching files with summary-match strings like "src orchestration ts orchestration_ws_methods orchestration ws methods" — this is just tokenized filename content, not useful context. Should provide brief architectural descriptions.

## What Worked Well

1. **Exact symbol lookup is solid.** When querying for a specific, named symbol, the definition consistently appeared at #1. The `OrchestrationEngineService` capsule immediately showed the interface and class. The `broadcastPush` capsule was clean and well-scoped.

2. **Multi-file clustering.** Capsules group results by directory/package (e.g., `[Cluster: server/src]`, `[Cluster: web/src]`). This helps orient the reader even when individual results are noisy.

3. **AST-aware compression levels are genuinely useful.** The `[skeleton]`, `[summary]`, `[full]`, `[reference]` levels provide good density control. Seeing a 1-line skeleton for a type definition is often exactly right — you know it exists without burning budget on the full schema.

4. **`cw_impact` is the strongest tool.** Found 44 affected symbols for `OrchestrationEngineService` with accurate import/call chains across 3 depths. This is genuinely difficult to replicate with Grep — you'd need multiple iterative searches. This is ContextWeave's clearest value-add.

5. **Honest LOW confidence on `broadcastPush`.** The capsule correctly flagged low confidence when the result set was thin. This is the desired calibration behavior — unfortunately not consistent (see P0 #1).

6. **Self-diagnostics are insightful.** The `packing_scatter` bottleneck diagnosis and suggestion to use story-complete packing for the architecture query showed genuine self-awareness of the failure mode.

**Summary judgment:** ContextWeave works well for single-symbol lookups where you know the exact name, and `cw_impact` is genuinely useful for blast-radius analysis. But for the two most important use cases — understanding end-to-end flows and grasping architecture — it performs worse than targeted Grep+Read. Confidence miscalibration is the most dangerous flaw: HIGH confidence on wrong answers means you can't trust it enough to skip verification, which eliminates the token savings. In this 88K LOC codebase, I would use `cw_impact` regularly but would not replace Grep+Read with capsules for flow tracing or architectural understanding.
