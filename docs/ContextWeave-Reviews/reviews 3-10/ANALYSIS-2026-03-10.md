## Step 2: Root Cause Diagnosis (Top 5 Findings)

### Root Cause 1: Confidence Miscalibration (8/8 reviews)

**Classification:** Threshold miscalibration + algorithm flaw

**Code path:** `src/capsule/confidence.ts:72-154`

The confidence computation has three surviving escape hatches:

1. **`intent !== "narrow"` gate (line 142):** For narrow and symbol-lookup intents, ALL utilization caps are skipped. A narrow query returning 320/1800 tokens (18%) can report HIGH.

2. **`thinRetrieval` gate (line 142):** If `retrievalSurfaceScore/relevantCoverage/noiseRatio` don't look thin, the caps are bypassed entirely — even at 6% utilization.

3. **`compactButGrounded` escape (lines 72-84, 143-148):** When `fileSummaryCount >= 2 && relevantCoverage >= 0.6`, the caps are raised to 0.78/0.82 instead of the CODEX_HANDOFF-specified 0.40/0.60. This condition is easily satisfied.

**Additional flaw in `formatter.ts:95`:** The text output (what agents actually read) uses binary LOW/HIGH with no MEDIUM:
```ts
const confidence = metadata.quality.lowConfidence ? "LOW" : "HIGH";
```
The MEDIUM tier exists in `buildStructuredOutput` but is invisible in the text path.

**Why the CODEX_HANDOFF fix didn't work:** 3 of the 4 specified changes were not made. The `compactButGrounded` escape was supposed to be removed; the `intent` gate was supposed to be removed; `tokenUtilization` was supposed to be made required. None of these happened. The partial fix (adding caps that are gated behind conditions that rarely fire) had no meaningful effect.

### Root Cause 2: Budget Underutilization (8/8 reviews)

**Classification:** Algorithm flaw (pipeline bottleneck upstream of packer)

**Code path:** `src/capsule/generator.ts:1013-1738`, `src/capsule/packer.ts:144-176`

The packer itself is correctly implemented — it has the iterative budget-filling loop targeting 85%. The problem is upstream:

1. **BFS node cap:** `maxVisitedNodes = Math.min(300, tokenBudget / 20)` (generator.ts:1013). For 8000-token budget → 300 max nodes. After filtering, only ~72 candidates reach the packer (hardCap, line 1494).

2. **Generator refill target mismatch:** The generator's refill loop targets 70% utilization (generator.ts:1734), not 85% as the packer allows. Even when the packer could fill more, the generator stops adding candidates at 70%.

3. **Stage-B filtering too aggressive:** The pipeline goes from ~120 stage-A candidates to ~20 stage-B (multiple reviews cite this). Stage-B filtering discards too many pivots.

4. **Packer can only pack what it receives:** If the scored nodes contain only 15 small symbols, the packer hits the budget ceiling early. It promotes L3→L0 and adds adjacent nodes, but there aren't enough adjacent nodes because the upstream pipeline didn't provide them.

**Why the CODEX_HANDOFF fix didn't work:** The fix correctly changed the refill gate (>=500, good) and added the packer loop (good), but left the upstream bottlenecks intact: BFS cap, hardCap, stage-B filtering, and refill target at 70% instead of 85%.

### Root Cause 3: Noise in Capsules (8/8 reviews)

**Classification:** Algorithm flaw (per-file backfill without per-symbol relevance filtering)

**Code path:** `src/capsule/generator.ts:1346-1409`

The `backfillWithinSelectedFiles` function adds **all symbols** from selected files at distance <= 2, scoring them by `lexicalScore * 1.5 + centrality * 4 + 0.25`. This means high-centrality irrelevant symbols in a relevant file outscore low-centrality relevant ones from other files.

When a file is selected because it contains one relevant symbol, ALL other symbols in that file become packing candidates with scores derived from centrality, not query relevance. This is why:
- `VerificationResult` (99 lines, high centrality) appears in every EBPS capsule
- `LandingHowItWorks` appears in a showToast query (same file imports showToast)
- `AdminSettingsPage` (218 lines) appears in a state management query
- `onNone`/`onSome` appear in an OrchestrationEngineService query

**The exact-name boost (0.1) helps the target symbol rank #1 but doesn't prevent backfill from filling 60-70% of remaining budget with noise.**

**Why the CODEX_HANDOFF fix didn't work:** The content fallback fix (0.2) correctly prevents the 90-pivot explosion on narrow queries. But the noise now comes from a different source: `backfillWithinSelectedFiles`, which was not addressed in the plan. The root cause shifted from content fallback to per-file backfill.

### Root Cause 4: Flow Tracing Failure (8/8 reviews)

**Classification:** Missing capability + edge case gap

**Code path:** `src/core/parser.ts` (edge creation), `src/mcp/tools/flow.ts` (traversal), `src/core/weighted-bfs.ts` (BFS weights)

The flow traversal itself works correctly — it follows all edge kinds including callback, server-action, route-handler. The failure is upstream in edge creation:

1. **JSX prop callbacks not indexed:** `onClick={handleClick}` does not create a callback edge. The parser only detects callbacks when a function identifier is passed as an argument in a regular call expression.

2. **IPC/event/WebSocket boundaries invisible:** `emit_all("gap_start")` → `listen('gap_start')` has no synthetic edge. String-based event connections between languages (Rust↔TS) or across HTTP/WS boundaries are not modeled.

3. **Method calls on variables not resolved:** `s.elapsed_ms()`, `app.emit_all()` — method calls through variables require type inference the parser doesn't perform.

4. **BFS weight table incomplete:** `weighted-bfs.ts:22-33` doesn't include `callback`, `server-action`, or `route-handler` edge weights. They fall back to generic cost 1.0.

5. **Path limit exhaustion on one branch:** DFS/BFS returns first N paths found, all through the same initial branch. No path diversity across distinct first-hop targets.

**Why the CODEX_HANDOFF fix didn't work:** 5.4 correctly added the edge types and route-handler detection, but JSX prop callbacks — the most common callback pattern in React codebases — were not implemented. Cross-boundary (IPC, WebSocket, HTTP) edge synthesis was not attempted.

---

### Root Cause 5: Follow-up Suggestions Quality (7/8 reviews)

**Classification:** Algorithm flaw (candidate pool contaminated by noise)

**Code path:** `src/capsule/formatter.ts:162-200, 355-363`

The query-aware ranking (text path, formatter.ts:183-200) uses `uncoveredHits` as primary sort — a good design. But:

1. **Candidate pool is the already-noisy packed symbol set.** Follow-ups are drawn from `visibleNodes` at compression level 1-2. If `backfillWithinSelectedFiles` injected irrelevant high-centrality symbols, those compete in the follow-up ranking.

2. **Secondary sort is `node.score` (centrality + locality), not query relevance.** When `uncoveredHits = 0` for all candidates (common when the query terms are already covered by L0 symbols), the ranking degenerates to pure score sort.

3. **Structured output path has NO query-awareness.** `buildStructuredOutput` (formatter.ts:355-363) sorts follow-ups by `node.score` only, completely ignoring query terms.

## Step 4: Research — How to Match Augment

### Augment's Current State (March 2026)

**Major shift since mid-2025:** Augment launched **Context Engine MCP** (February 2026), exposing their retrieval pipeline as an MCP server. This is a direct competitive move into ContextWeave's space. Two deployment modes:
- **Local mode** ("Auggie" CLI as MCP server): real-time context from working directory
- **Remote mode** (`api.augmentcode.com/mcp`): cross-repository context from hosted persistent index

**Scale claims:** 400K–1M+ files per workspace, real-time knowledge graph, multi-repo awareness.

**Pipeline (confirmed via blog posts, SDK docs, CMU co-authored paper):**
1. Tree-sitter AST parsing for structure-preserving chunking (confirmed by cAST paper, EMNLP 2025, co-authored by Jiayi Wei from Augment)
2. Dense vector embeddings for semantic search
3. Dependency graph traversal (PageRank-like on call graphs)
4. Cross-repo indexing via persistent cloud infrastructure
5. Architectural pattern detection (active vs deprecated code paths, team conventions)

**Benchmark (300-PR Elasticsearch, 3.6M Java LOC):**
- Augment alone: +12.8 vs human baseline
- Claude Code alone: -11.8
- Claude Code + Context Engine MCP: **80% improvement** in task completion
- Cursor + Context Engine: **71% improvement** (completeness +60%, correctness ~5x)

**Key insight from Augment's "Context Engine vs RAG" guide:** They identified a 47-point gap between benchmark RAG performance (65-71%) and production deployments (17.67%). This matches exactly what ContextWeave's 8 field reviews found — the gap between "has the components" and "actually works in the field."

### State of the Art in Code Retrieval (2025-2026)

**1. AST-Aware Chunking (cAST, CMU + Augment, EMNLP 2025)**
- Recursive split-then-merge on AST: top-down subdivision → bottom-up sibling merging
- Results: Recall@5 +4.3, Precision +1.2-3.3 (RepoEval); Pass@1 +2.67 (SWE-bench)
- Key finding: **merging is as important as splitting** — split-only produces too many tiny chunks
- Reference: https://github.com/yilinjz/astchunk
- ContextWeave status: Has AST parsing + symbol extraction but chunks not stored by AST node boundaries

**2. Hybrid BM25 + Dense Vector (Industry Standard)**
- BM25 essential for exact identifiers; embeddings for semantic queries
- RRF (Reciprocal Rank Fusion) is the dominant fusion method (parameter-free, robust)
- No consensus on optimal code embedding model (CodeBERT, StarCoder, general-purpose all compete)
- ContextWeave status: Has BM25 + vector hybrid with RRF. Gap is in quality, not presence.

**3. GraphRAG for Code**
- lxDIG-MCP (open source, Feb 2026): three-plane fusion (property graph + vector + BM25 + RRF)
- Global search for architecture questions; local search for targeted queries
- ContextWeave status: Has structural graph (PageRank, BFS). Missing: semantic graph edges.

**4. Context Compression (Acon, Microsoft 2025)**
- Trained compressor for agent interaction history: 26-54% memory reduction, 95%+ performance preserved
- ContextWeave status: Has token-budgeted packing (multi-level compression). Could benefit from learned compression.

### Open-Source Competitive Landscape

| Project | Approach | Assessment vs ContextWeave |
|---------|---------|---------------------------|
| **lxDIG-MCP** | Graph + Vector + BM25 + RRF | Architecturally closest but requires Docker + Memgraph + Qdrant. Not local-first. |
| **DeepContext MCP** | Symbol-aware semantic search | Requires external API key. Not self-contained. |
| **semantic-search-mcp** | Local embeddings (MiniLM), SQLite | Similar approach but no dependency graph, no impact analysis. |
| **Augment Context Engine MCP** | Full pipeline, cloud or local CLI | Production-grade competitor but cloud-dependent. Not open source. |

**Assessment:** No open-source tool matches ContextWeave's feature set (AST graph + impact analysis + token-budgeted packing + cross-session memory). The gap is in retrieval quality, not capability breadth.

### Techniques Worth Implementing

| Technique | Impact | Effort | Runs Locally? | Priority |
|-----------|--------|--------|--------------|----------|
| **Cross-encoder reranking** | +30-40% retrieval accuracy | Medium (3-4 days) | Yes (ms-marco-MiniLM, ~85MB, ONNX) | **HIGH** — highest quality-to-effort ratio |
| **HyDE query expansion** | Medium (best for NL queries) | Low (1-2 days) | Yes (uses ambient Claude call) | **MEDIUM** — low cost, moderate gain |
| **Multi-hop retrieval** | High for architectural queries | Medium (2-3 days) | Yes (control flow pattern) | **MEDIUM** — formalizes existing refill pass |
| **Speculative retrieval (SpecAgent)** | +48-58% relative (REPOCOD) | Medium-High (3-5 days) | Yes (LLM at index time) | **MEDIUM** — high impact but indexing cost |
| **ColBERT late interaction** | High quality | Very High (2-4 weeks) | Yes but heavy engineering | **LOW** — cross-encoder gives similar gains cheaper |
| **GNN on AST graphs** | High quality | Very High (needs PyTorch) | Impractical in TS | **SKIP** — existing PageRank captures most structural signal |

**Recommendation:** Cross-encoder reranking is the single highest-ROI addition. After fixing the 10 core bugs (confidence, noise, budget), adding a cross-encoder reranking pass after hybrid search would provide the largest quality jump for the least engineering effort. The model (`cross-encoder/ms-marco-MiniLM-L-6-v2`, ~85MB) runs fully locally via `@huggingface/transformers` ONNX, at ~50-150ms per batch of 20 candidates.

### The Gap Is Not in Architecture — It's in Execution

ContextWeave now has the same architectural components as Augment (AST parsing, embeddings, hybrid search, graph expansion, token-budgeted packing). The 8 field reviews prove the components exist. What's missing is execution quality:

| Component | Augment (estimated) | ContextWeave (measured) |
|-----------|-------------------|------------------------|
| Retrieval precision | ~80% (from benchmarks) | ~35% (broad recall 3.4/10) |
| Budget utilization | ~85%+ | 14-33% on large budgets |
| Confidence accuracy | Trustworthy | HIGH on wrong answers (3.8/10) |
| Flow tracing | Cross-service | Import edges only (3.4/10) |
| Token savings | ~60-70% (claimed) | ~0% quality-adjusted |

The fix plan in Step 5 targets closing this execution quality gap with the existing architecture.

### Fix 1: Confidence Calibration — Remove All Escape Hatches

**Finding:** HIGH confidence on wrong/incomplete answers in 8/8 reviews. Average confidence calibration score: 3.8/10.

**Root cause:** Three escape hatches in confidence.ts prevent utilization caps from firing: `intent !== "narrow"` gate, `thinRetrieval` gate, `compactButGrounded` escape. Text formatter uses binary LOW/HIGH with no MEDIUM.

**Source files:** `src/capsule/confidence.ts`, `src/capsule/formatter.ts`

**Implementation:**

In `confidence.ts`:
1. Delete the `compactButGrounded` computation (lines 72-84) and all references to it (lines 143-148)
2. Remove the `intent !== "narrow" && intent !== "symbol-lookup"` condition from line 142 — apply caps to ALL intents unconditionally
3. Remove the `thinRetrieval` gate from line 142 — apply caps unconditionally based on `tokenUtilization` alone
4. Make `tokenUtilization` required (remove the `?` from the type)
5. Apply these caps unconditionally:
   - `tokenUtilization < 0.30` → cap confidence at 0.40
   - `tokenUtilization < 0.50` → cap confidence at 0.60
   - Never return > 0.90 unless `tokenUtilization > 0.60 AND pivotCoverage > 0.60`

In `formatter.ts` line 95:
6. Replace binary LOW/HIGH with three tiers:
   ```
   confidence < 0.45 → "LOW"
   confidence < 0.75 → "MEDIUM"
   confidence >= 0.75 → "HIGH"
   ```

**Test:** Query that uses 320/1800 tokens (18% utilization) must report LOW or MEDIUM, never HIGH. Query with 14% utilization (t3code architecture) must report LOW.

**Expected impact:** Confidence calibration score from 3.8 → 6+. Agents can trust the confidence signal and skip verification on HIGH, reducing total token cost.

### Fix 2: Budget Filling — Fix the Pipeline, Not Just the Packer

**Finding:** 14-33% utilization on 8K budgets in 8/8 reviews. Average budget utilization score: 3.8/10.

**Root cause:** BFS hardCap limits candidates to 72 for broad queries. Generator refill targets 70% not 85%. Stage-B filtering is too aggressive.

**Source files:** `src/capsule/generator.ts`, `src/capsule/packer.ts`

**Implementation:**

In `generator.ts`:
1. Change refill target from 0.70 to 0.85 (line 1734)
2. For broad/task queries: when post-refill utilization is still < 0.50, run a second expansion pass:
   - Double the hardCap (72 → 144)
   - Re-run BFS with relaxed stage-B filtering (lower lexical threshold by 30%)
   - Re-pack with the expanded candidate pool
3. When `tokenBudget >= 4000` and utilization < 0.40 after first pack, switch to "story-complete" packing mode: select the top 3-5 files by relevance and show them at full/summary compression instead of spreading across 10+ files at skeleton level

In `packer.ts`:
4. When utilization < 0.50 after the promotion pass: for each L0/L1 file, fetch ALL symbols from the file (not just the ones from BFS) and include them at L2/L3 until budget is filled. This ensures files that ARE selected get deep coverage rather than shallow skeleton.

**Test:** 8K budget query on any codebase returns >= 4000 tokens (50% utilization minimum).

**Expected impact:** Budget utilization from 3.8 → 6+.

### Fix 3: Noise Elimination — Per-Symbol Relevance Filtering

**Finding:** 25-70% of capsule tokens are irrelevant symbols in 8/8 reviews. Average broad recall: 3.4/10.

**Root cause:** `backfillWithinSelectedFiles` adds all symbols from selected files using centrality scoring, not query relevance.

**Source files:** `src/capsule/generator.ts`

**Implementation:**

In `generator.ts`, `backfillWithinSelectedFiles` function (lines 1346-1409):
1. Before adding a backfill symbol, compute its lexical overlap with the original query terms. If overlap is 0 AND the symbol is not a direct caller/callee of a pivot symbol, skip it.
2. Replace the scoring formula `lexicalScore * 1.5 + centrality * 4 + 0.25` with `queryRelevance * 6 + lexicalScore * 1.5 + centrality * 2 + 0.25` where `queryRelevance` is the ratio of query terms present in the symbol's name, signature, or containing file path.
3. Add a relevance floor: symbols with `queryRelevance = 0 AND directEdgeToPivot = false` get a hard 0.5x penalty.

Additionally, add a test-file penalty:
4. When mode is `review` or `feature`, apply a 0.3x scoring multiplier to symbols from files matching `test`, `spec`, `mock`, `fixture`, `__tests__`, `__mocks__` patterns. Only boost test files when mode is `debug`.

**Test:** Query "showToast" should NOT include `LandingHowItWorks`, `getAllProfiles`, or `isProtectedPath`. Query "risk management" should NOT include `checksums` or `isRecord`.

**Expected impact:** Noise in capsules from 40-70% → <20%. Broad recall improves because budget freed from noise goes to relevant files.

### Fix 4: Flow Tracing — JSX Callbacks + Path Diversity

**Finding:** cw_flow non-functional in 8/8 reviews. Average flow tracing score: 3.4/10.

**Root cause:** JSX prop callbacks not indexed. No cross-boundary edge synthesis. Path limit exhausted on one branch.

**Source files:** `src/core/parser.ts`, `src/mcp/tools/flow.ts`, `src/core/weighted-bfs.ts`

**Implementation:**

In `parser.ts`:
1. Add JSX prop callback detection: when a `jsx_attribute` has a value that is an identifier matching a known symbol, create a `callback` edge from the JSX component to that symbol. Pattern: `<Component onClick={handleClick} />` → callback edge from Component render to `handleClick`.

2. Add "use server" detection: when a function body starts with the string literal `'use server'`, tag it and create a `server-action` edge from any import of that function.

In `weighted-bfs.ts`:
3. Add missing edge weights: `callback: 0.7`, `server-action: 0.7`, `route-handler: 0.7` to the EDGE_WEIGHTS table.

In `flow.ts`:
4. Add path diversity: instead of returning the first N paths from BFS, bucket paths by their first-hop target. Ensure each distinct first-hop callee gets at least 1-2 paths before any branch gets more than 3.

5. Add incoming flow support: add a `direction: "incoming" | "outgoing" | "both"` parameter. For "incoming", query edges WHERE `target_symbol_id = ?` instead of `source_symbol_id = ?`.

**Test:** `cw_flow("handleSubmit")` in a React app with `<form onSubmit={handleSubmit}>` should trace the callback edge. `cw_flow("_run_single_client")` should show paths through all 4 pipeline branches, not just extraction.

**Expected impact:** Flow tracing from 3.4 → 5+. Still won't cross HTTP/WebSocket boundaries (that's a Tier 2 enhancement).

### Enhancement 1: Cross-Encoder Reranking Pass

**What it does:** After initial retrieval, re-score each candidate against the query using a cross-encoder model that sees both query and candidate together (not just separate embeddings). MIT study (Jan 2026) shows +33-42% accuracy improvement. Reranking leaderboard: best open model is `ms-marco-MiniLM-L-6-v2` (~1400 ELO).

**How Augment does it:** Likely uses a proprietary reranker. Industry standard is two-stage: fast retrieval (BM25+vector) → slow reranking (cross-encoder).

**Implementation approach:**
1. After hybrid search returns top-50 candidates, run each through `cross-encoder/ms-marco-MiniLM-L-6-v2` via `@huggingface/transformers` ONNX runtime
2. Re-sort by cross-encoder score
3. Pack top-N into capsule
4. Latency: ~50-150ms per batch of 20 candidates on CPU — acceptable in a 2-second retrieval budget

**Runs locally?** Yes — ~85MB model, ONNX, no API keys.

**Estimated complexity:** Medium (3-4 days)

**Expected impact on "Would replace Grep+Explore?" score:** +15-20% — highest quality-to-effort ratio of any enhancement. The single most impactful addition after fixing core bugs.

---

### Enhancement 2: Cross-Boundary Edge Synthesis

**What it does:** Automatically create synthetic edges for event-based connections: `emit("X")` → `listen("X")`, `fetch("/api/Y")` → `export function GET/POST` in matching route, Convex `useMutation(api.X.Y)` → mutation handler.

**Implementation approach:**
1. During indexing, extract string literals from `emit`, `emit_all`, `fetch`, `invoke` calls
2. Extract string literals from `listen`, `on`, `addEventListener` registrations
3. For `fetch("/api/X")` patterns, match to files at `app/api/X/route.ts`
4. Create `framework_entry` or `event` edges between matched pairs
5. For Convex/tRPC, match `api.X.Y` patterns to mutation/query exports

**Runs locally?** Yes — pure AST analysis.

**Estimated complexity:** Large (5-7 days) — many framework-specific patterns to handle.

**Expected impact:** High for apps with IPC/event architectures (Nudgy, t3code, lawn). Would make cw_flow actually useful for cross-boundary tracing.

---

### Enhancement 3: Query-Type-Specific Pipelines

**What it does:** Route different query types through different retrieval pipelines instead of one-size-fits-all.

**Implementation approach:**
- `symbol-lookup` → Direct AST lookup + immediate callers/callees. No BFS. No backfill.
- `narrow` → Hybrid search (top 10) + 1-hop graph expansion. Moderate backfill.
- `broad/task` → Hybrid search (top 30) + 2-hop graph expansion. Story-complete packing. Aggressive backfill.
- `debug` → Include test files, error patterns, stack trace matching.

**Estimated complexity:** Medium (3-4 days) — the intent classifier already exists, just needs pipeline branching.

**Expected impact:** Medium-High — prevents symbol lookups from going through broad retrieval (current source of noise).

---

### Enhancement 4: HyDE for Natural Language Queries

**What it does:** For queries without code identifiers (e.g., "how does authentication work across the app"), generate a hypothetical code snippet that would answer the query, embed THAT, then search for similar real code. Closes the query-document distribution gap.

**Implementation approach:**
1. Detect NL queries (heuristic: no camelCase/snake_case tokens)
2. Use the ambient Claude call to generate a hypothetical function signature + docstring (~50 tokens)
3. Embed the hypothetical document instead of the raw query
4. Proceed with normal hybrid search

**Runs locally?** Yes — uses the same LLM already available via MCP.

**Estimated complexity:** Low (1-2 days)

**Expected impact:** Medium — works best for broad/architectural queries where keyword search fails. Risk: hallucinated hypotheticals can degrade retrieval. Mitigate by generating signature+docstring only (not full implementation).

---

### Enhancement 5: Multi-Hop Retrieval in Capsule Pipeline

**What it does:** After initial retrieval, check if the query spans multiple modules. If so, run a second retrieval hop using symbols found in the first hop as seeds. Based on HopRAG (ACL Findings 2025) approach of traversing a passage graph.

**Implementation approach:**
1. After first capsule pack, if `queryIntent === "broad"` AND `pivotCoverage < 0.50`:
   - Extract symbol names from packed results
   - Generate follow-up queries: "callers of X", "files importing Y"
   - Run BFS from these new seeds
   - Merge new candidates with existing, re-pack
2. Limit to 2 hops maximum to control latency

**Runs locally?** Yes — pure control flow, no model needed.

**Estimated complexity:** Medium (2-3 days)

**Expected impact:** High for cross-file architectural queries. The current refill pass is a crude version of this; formalizing it would significantly improve broad recall.

---

### Enhancement 6: Speculative Retrieval ("What Will the Agent Need Next?")

**What it does:** After returning a capsule, pre-compute likely follow-up queries and cache their results. When the agent asks the predicted question, return instantly.

**Implementation approach:**
1. After a capsule is returned, identify symbols that were compressed or mentioned but not shown
2. Pre-compute capsules for the top 3 likely follow-up queries
3. Cache in memory (TTL 5 minutes)
4. On next capsule request, check cache first

**Estimated complexity:** Medium (2-3 days)

**Expected impact:** Low-Medium — reduces latency but doesn't fix quality.
