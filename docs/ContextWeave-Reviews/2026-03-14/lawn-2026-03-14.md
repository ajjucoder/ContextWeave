## Flaws Found

Ordered by severity. Each flaw includes what happened, why, and how to fix it.

### P0 (Critical — blocks adoption)
1. **Broad architectural retrieval can point at the wrong subsystem**: The route-data architecture query ranked `app/routes/for.agencies.tsx` first and suggested narrowing to that file. This is a direct failure on the kind of “explain the system” question ContextWeave exists to answer. Root cause is likely broad-query ranking/packing in `src/capsule/generator.ts` and related scorers not penalizing irrelevant high-level route files strongly enough. Fix: architecture/broad mode needs query-fit gating, stronger helper/module-name weighting, and a sanity check that suppresses absurd path suggestions when top results are semantically disconnected.
2. **Flow tracing misses real Convex call edges**: `cw_flow("getSharedPlaybackSession" -> "getByShareGrant")` failed even though the source contains an explicit `ctx.runQuery(api.videos.getByShareGrant, ...)`. `cw_flow("processWebhook", direction="incoming")` failed even though `convex/http.ts` calls it through `ctx.runAction(internal.muxActions.processWebhook, ...)`. Root cause is almost certainly missing edge extraction/resolution for Convex `api.*`/`internal.*` references and HTTP route-handler edges, likely in the indexer/graph construction path rather than the flow formatter itself. Fix: add graph edges for `runQuery`, `runMutation`, `runAction`, generated API refs, and `http.route` handler targets; add regression tests on Convex codebases.
3. **Impact analysis is untrustworthy on API-backed symbols**: `cw_impact("resolveContext")` returned “No dependents found” even though `app/routes/dashboard/-team.data.ts`, `-project.data.ts`, `-video.data.ts`, and `-settings.data.ts` all depend on `api.workspace.resolveContext`. Root cause is the same graph-resolution gap showing up in `src/mcp/tools/impact.ts` and symbol-resolution/indexing logic. Fix: resolve generated API member references back to exported server symbols before building impact edges.

### P1 (Important — degrades quality)
1. **Broad task capsules still miss the actual bridge file**: The share-link flow capsule missed `convex/shareLinks.ts`, which is where `issueAccessGrant` lives, and instead over-indexed on `comments` noise. Root cause is ranking that rewards high-frequency surface terms over low-frequency bridge functions. Fix: boost rare exact symbol hits and flow-bridge files when the query implies a stepwise pipeline.
2. **Confidence is still miscalibrated for broad/common-name queries**: `cw_capsule("comments", 1200)` reported `HIGH` confidence and `VERY_LOW` uncertainty while surfacing mostly local `comments` variables, not the core comments module. Root cause is confidence scoring that treats pivot saturation as success without checking whether the pivots are semantically the right kind of result. Fix: incorporate definition precision, module concentration, and consumer/producer mix into confidence.
3. **Budget utilization is far below the claimed operating model**: On 8k budgets, capsules used only 14-15% of available budget. That means the packer is either giving up early or never finding enough coherent material. Root cause is likely in the packer/budget loop in `src/capsule/generator.ts`. Fix: continue filling with coherent supporting snippets until the budget is meaningfully used, or explicitly report why the packer stopped early.
4. **`cw_recall` is too polluted by auto-generated observations**: Recall for `share link access` mostly returned a prior capsule summary plus passive auto-observations. That is not useful memory; it is just replaying earlier retrieval mistakes. Root cause is memory search including passive observations by default and storing low-value capsule-insight notes too aggressively, likely in `src/memory/search.ts` / `src/mcp/tools/recall.ts`. Fix: default to intentional observations for code questions and heavily downweight passive capsule summaries.
5. **Session stats overstate value**: `cw_stats` only counts capsule tokens, not the `cw_grep`/`cw_read` follow-ups that were necessary to finish Tasks B and C, yet it can still declare utilization “healthy.” Root cause is metric scope mismatch in `src/mcp/tools/stats.ts`. Fix: either track all context-producing tool calls or stop presenting the output as a savings/value summary.
6. **Setup friction is still real**: This repo already had `.mcp.json` pointing at a valid local ContextWeave install, but the server was not exposed as connected MCP tools in this agent session. That is not a retrieval bug, but it absolutely hurts replacement value in the field. Fix: harden install/registration diagnostics and surface a one-command health check that proves the MCP server is live in the current agent runtime.

### P2 (Moderate — papercut)
1. **`cw_grep` exact symbol lookup is source-agnostic by default**: Exact-text search for `resolveContext` and `prewarmSpecs` ranked tests/docs/import sites above the definition. Fix: add source-first ranking or a default `scope=code` mode.
2. **Follow-up suggestions can be actively bad**: Task C recommended reading `handleDownloadVideo` and narrowing the query to `for.agencies.tsx`. Root cause is follow-up generation using packed-symbol score rather than query-fit. Fix: score follow-up suggestions with a stronger relevance threshold in `src/capsule/formatter.ts`.
3. **Status/reindex messaging is confusing on incremental runs**: CLI reindex reported `142 files, 0 symbols (58ms)` because everything was skipped, plus `1 files had parse errors`, while normal status output did not surface parse-error count clearly. Fix: distinguish total indexed state from delta processed state and show parse errors prominently in status.

## What Worked Well

- Exact symbol lookup is decent for distinctive symbols like `issueAccessGrant` and `resolveContext`; capsules put the definition first.
- `cw_read` is genuinely good once you already know the symbol or file you need.
- `cw_overview` becomes useful when manually narrowed to the right subtree.
- `cw_flow` can see simple UI-to-Convex mutation edges like `SharePage -> issueAccessGrant`.
